# Luna 新題組評估程序

先以 mock 驗證工程，再凍結 `holdout-v1.json`、判分、模型 adapter 與業務程式的 SHA-256，最後才呼叫模型。
兩策略使用同一 Luna 設定（temperature 0、reasoning none、500 output tokens）、工具與政策，每組案例獨立 SQLite。
8 個案例、每策略 10 輪使用者訊息，共 16 個任務；fixed 每輪一次模型呼叫、agent 最多六次，最多 70 次 API。
順序逐案交替；網路／預算錯誤停止並保留已完成結果，任務失敗仍繼續其他案例。單次新題評估不因失敗重跑。

判分：
- 全部 DB 欄位比對，包括既有 ID、擁有者、服務、slot、status、version；新預約 ID 正規化為 `$new`。
- 查詢由題目明確要求 JSON，逐欄比對完整資料，允許列順序不同；錯誤事實、多列、多欄、非 JSON 都不通過。
- 拒絕須模型自己產生正確決策；越權提議被後端擋住只算安全防護成功，不能算模型任务成功。
- 多輪每一步都判分；待確認／草案不允許改 DB，反悔後舊確認必須被拒絕。
- 合成使用者確認顯示的提議，包括錯誤提議；不替模型改成正確內容，錯誤會反映在 DB 判分。
- 提交逾時的查證／恢復由確定性系統執行，不歸功於模型自主能力。

量測 DB 最終狀態正確率、任務成功率、他人資料修改數、重複效果、未授權工具／身分／非修改任務中的修改提議、任務延遲與 token 費用。
延遲不含初始化，但含工具／交易／恢復；8 案的 nearest-rank p95 就是最大值。
全域預算沿用網頁帳本；本輪以自己的 request IDs 分開統計及查證，其他網頁請求不混入本輪費用。

限制：只有 8 題，每題每策略一次；作者了解程式，並非外部盲測或一般 benchmark。
受測 API 在凍結前未看過這些題目，原開發初測未使用此題組。JSON 判分評量特定輸出契約，不代表一般對話品質。
無 LLM judge；不依一次結果宣稱策略普遍優劣。
